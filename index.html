0.1The answer formula

“Secure” is not a complete sentence. Every strong exam answer names four things:

security claim = property + asset + adversary model + assumptions

Weak: “HTTPS is secure.” Strong: “TLS protects the confidentiality and integrity of application data against a network attacker who cannot compromise the endpoints or break the cryptography.”

For attack scenarios, use the five-part pattern from Week 4: asset → required property → attacker position → attacker behaviour → consequence. Say “the mode/parameter was misused” rather than “AES is broken” when that is what happened.

1.1Security properties

A property always belongs to an asset (password, session cookie, transfer command, audit log, the service itself). “We need integrity” is incomplete until you say integrity of what. The STRIDE column is the threat that violates each property; STRIDE is covered in §1.2.

  • Entity authentication: the party in the protocol right now is who it claims (e.g. checking a server certificate). Data-origin authentication: this message was produced by a holder of the credential (e.g. a signed update). Talking to Bob does not prove Bob wrote every later object.
  • Authentication ≠ authorization. A valid identity can still issue commands it is not allowed to issue.
  • Non-repudiation is evidence for a third party. Integrity says “not changed”, authentication says “who produced it”, non-repudiation says “can this be shown to someone else”. 1.2Threat modeling

threat model = assets + actors + trust + attacker capabilities

It is a structured way to decide what can go wrong and what matters, and it states what is inside and outside the security claim. For every asset ask: what if it is read, changed, deleted, forged, or made unavailable?

  • Actors and privilege: trust is contextual (student, lecturer, admin, web server, database). Privilege boundaries become attack goals.
  • Trust boundary: wherever data crosses one (untrusted network → web server → database), ask what happens if the attacker controls it. Treat the network as untrusted unless stated otherwise.
  • Attack surface: every interface the adversary can interact with (TCP 22 SSH, 80 HTTP, 443 HTTPS, UDP 53 DNS, admin API). Surface is not automatically a vulnerability, but every exposed parser needs analysis; reducing exposure is a defence.
  • STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) is a checklist for generating threats, mapped to properties in the table above. It gives a memory aid and shared vocabulary. It is not a proof, not a complete attacker model, and does not guarantee all threats were found.
  • Attack trees: root = attacker goal, branches = ways to reach it, leaves = concrete steps. OR node: any child suffices (sniff or phish the password). AND node: all children needed (capture traffic and obtain key). Annotate paths with cost, skill, time and detectability to compare them. Guessing a weak password is cheap; breaking AES-256 is “astronomical, not feasible”.

1.3Adversary models

Ask about capabilities before labels: can the attacker observe? modify, replay, drop, inject? send but not see responses? compromise endpoints? how much computation? which keys or tokens do they hold?

These are two separate dimensions. On-path does not mean active; the Week 1 lab sniffer is a passive on-path attacker.

Dolev–Yao (symbolic) model: “perfect crypto, hostile network”

  • The attacker controls the network: read, block, delay, reorder, replay, inject, modify, impersonate.
  • Cryptography is treated as ideal: seeing Enc_K(M) without K reveals nothing; with K she can decrypt. She can pair known terms (A,B) and split pairs.
  • Purpose: find protocol logic flaws (replay, missing authentication, state mistakes) even with perfect primitives. It does not mean the attacker can break AES.

Replay is the cleanest example T3: Eve resends yesterday’s Enc_K("transfer 100"). She never decrypts it, yet the protocol fails if it accepts stale messages. Freshness needs nonces, sequence numbers, timestamps or state.

Computational model

  • Efficient attacker = PPT (probabilistic polynomial time) algorithm.
  • Security game: challenger picks hidden bit b ∈ {0,1}, adversary outputs guess b′. Guessing alone wins half the time, so Adv = |Pr[b′ = b] − 1/2|. The IND-CPA game in §2.6 is the concrete version.
  • Negligible: eventually smaller than 1/λ^c for every constant c. So 2^−λ is negligible; 1/λ and even 1/λ^100 are not.

Week 2 · lecture + lab

2 · Symmetric crypto

2.1What encryption does and does not give

Encryption primarily gives confidentiality. It does not automatically give integrity, authentication, freshness or availability T3. Even with Enc_K("PAY 100") the ciphertext can be modified, the wrong peer can be authenticated, an old ciphertext can be replayed, or an endpoint can be compromised. For the message MEET AT 10: confidentiality asks “can Eve read it?”, integrity asks “can Eve change it to 11 undetected?”, authentication asks “does Bob know who sent it?”. Authenticated encryption aims for confidentiality and integrity together §2.5.

Unreadable data can still be malleable. Confidentiality does not imply integrity.

2.2Perfect secrecy and the one-time pad

Perfect secrecy: seeing the ciphertext gives no information about the plaintext, even to an attacker with unlimited computation.

Pr[M = m | C = c] = Pr[M = m] OTP: C = M ⊕ K, M = C ⊕ K (since K ⊕ K = 0)

It works because for every candidate plaintext of the same length there is a key that maps it to the observed C, so no plaintext is favoured. Example: M=10110010, K=01101001 gives C=11011011.

Four requirements: the key is truly random, at least as long as the message, kept secret, and never reused. These kill it for Internet traffic: a 10 GB file needs 10 GB of pre-shared key, and if you can deliver that key securely you have nearly solved the original problem (key distribution).

Reuse is catastrophic T5:

C₁ ⊕ C₂ = (M₁ ⊕ K) ⊕ (M₂ ⊕ K) = M₁ ⊕ M₂

The key cancels and the attacker learns a direct relationship between plaintexts. The same failure returns in CTR mode §2.5.

2.3Computational security

Practical cryptography relaxes “unlimited attacker learns nothing” to “no efficient (PPT, §1.3) attacker gains meaningful advantage”, which allows a short, reusable key. AES is not claimed mathematically unbreakable; the claim is practical infeasibility when used correctly. Symmetric correctness: Dec_K(Enc_K(M)) = M; Week 2 assumes K already exists (key establishment is §3.4).

2.4Block ciphers and AES

  • A block cipher maps fixed-size blocks; AES block = 128 bits = 16 bytes, always. It does not say how to encrypt a 1 MB file; that is the job of a mode.
  • Under a fixed key it must be a permutation (one-to-one), or decryption would be ambiguous.
  • PRP (pseudorandom permutation): without K, the keyed bijection should be computationally indistinguishable from a random permutation. AES is not random; it is designed to look random.
VariantKeyRounds

The 16 bytes form a 4 × 4 state. After an initial AddRoundKey, each round applies:

StepWhat it doesRole
SubBytesEach byte through the S-box; nonlinear, so the cipher is not one big solvable linear systemConfusion

Confusion (Shannon): make the key–ciphertext relationship complex. Diffusion: spread each plaintext bit’s influence across the ciphertext. Together they give the avalanche effect: flip one input bit and, after enough rounds, many output bits change.

2.5Modes of operation

Security = AES + mode + parameter management. AES is a block cipher; ECB / CBC / CTR / GCM are modes T3.

ECB (Electronic Codebook)

Cᵢ = E_K(Pᵢ), each block independently. AES is deterministic under a fixed key, so Pᵢ = Pⱼ ⇒ Cᵢ = Cⱼ: equality and structure leak (the ECB image still shows the picture; repeated USER rows stay visible). Unreadable ≠ secure. Do not use ECB for ordinary data.

CBC (Cipher Block Chaining)

C₁ = E_K(P₁ ⊕ IV) Cᵢ = E_K(Pᵢ ⊕ Cᵢ₋₁) decrypt: Pᵢ = D_K(Cᵢ) ⊕ Cᵢ₋₁
  • The IV randomises the first block; it is usually public and sent as IV ‖ C₁ ‖ C₂ ‖ …, but must be generated correctly (unpredictable).
  • Needs padding to whole 16-byte blocks. Distinguishable invalid-padding errors led to padding oracle attacks (reappear in TLS as Lucky13/POODLE, §6.3).
  • Malleable: flipping bits in Cᵢ₋₁ flips the same bits in Pᵢ. CBC alone ≠ integrity.

CTR (Counter)

Sᵢ = E_K(N ‖ i) Cᵢ = Pᵢ ⊕ Sᵢ Pᵢ = Cᵢ ⊕ Sᵢ
  • Turns the block cipher into a stream-like cipher: parallelisable, no CBC-style padding (only the needed keystream bytes are used).
  • Never reuse a nonce under the same key T5. Same nonce + key ⇒ same keystream ⇒ the OTP failure: C₁ ⊕ C₂ = M₁ ⊕ M₂. If one plaintext is known: M₂ = C₁ ⊕ C₂ ⊕ M₁.
  • Malleable even with correct nonces: C′ = C ⊕ Δ ⇒ P′ = P ⊕ Δ. CTR alone is not message authentication.

GCM / AEAD

AEAD = Authenticated Encryption with Associated Data: confidentiality plus integrity in one construction, instead of hand-combining a mode and a MAC. Associated data is metadata that is authenticated but not encrypted. GCM = CTR-like encryption + an authentication tag over the ciphertext and associated data. Output: nonce ‖ ciphertext ‖ tag. Rules: verify the tag before using any plaintext; nonce reuse is also dangerous here. TLS’s use of AEAD is in §6.3.

2.6IND-CPA: confidentiality as a game

  1. The attacker may request encryptions of messages of its choice (chosen-plaintext).
  2. It submits two equal-length messages M₀, M₁.
  3. The challenger encrypts M_b for a hidden random bit b and returns C.
  4. The attacker wins by guessing b better than chance: Adv = |Pr[b′ = b] − 1/2|.

ECB fails because it is deterministic and leaks equal blocks (and the attacker can ask for encryptions of the challenge messages). CBC needs unpredictable IVs, CTR needs unique nonces, GCM needs nonce discipline and tag verification to reach the goal.

Week 2 lab. Implement ECB vs CTR around a library block cipher. (1) Encrypt an image with ECB: pixel values unreadable, structure leaks. (2) Reuse a CTR nonce: XOR two ciphertexts to get M₁ ⊕ M₂, then recover the unknown plaintext from a known one.

3 · Integrity & public key

Week 2 showed confidentiality is not enough (CTR is malleable). Week 3 asks how to detect modification and how to bind messages and keys to identities.

3.1Hash functions

H : {0,1}* → {0,1}ⁿ: any-length input, fixed n-bit digest. Deterministic (same input → same digest), with avalanche ("hello" vs "Hello" give unrelated digests). Hashing is not encryption; there is no “decrypt the hash”.

PropertyAttacker is givenGoalGeneric work (ideal n-bit hash)
Preimage (“one-way”)digest hfind m with H(m) = h≈ 2ⁿ
Second preimagemessage mfind m′ ≠ m with H(m′) = H(m)—
Collisionnothing fixedfind any m₁ ≠ m₂ with H(m₁) = H(m₂)≈ 2ⁿᐟ² (birthday)

Birthday bound: q samples give about q(q−1)/2 pairs, so a collision becomes likely once q² ≈ N = 2ⁿ, i.e. q ≈ √(2ⁿ) = 2ⁿᐟ². Collisions are easier than preimages because the attacker chooses both messages.

A “256-bit hash” does not have 256-bit collision resistance. SHA-256 generic collision security ≈ 2¹²⁸.

A plain hash does not authenticate. If Alice sends "PAY BOB 100", H(msg), Eve changes the message to "PAY EVE 900" and recomputes the hash; the algorithm is public. The receiver needs a secret-dependent tag. Hence MACs.

3.2MACs, length extension, HMAC

A MAC takes a secret key and a message and outputs a tag t = MAC_K(m); the receiver recomputes it with the same key. Valid tag ⇒ integrity + shared-key data-origin authentication (“someone holding K made this”). A MAC gives no confidentiality: m may be plaintext. Encryption-only is the mirror image: unreadable but modifiable.

The tempting construction: tag = H(K ‖ m)

With a Merkle–Damgård hash (SHA-1, SHA-256), the digest is the final internal chaining state. An attacker who sees m and H(K ‖ m) can keep hashing from that state:

  1. Guess the secret length len(K) (try plausible values).
  2. Compute the glue padding the hash would have added to K ‖ m.
  3. Continue hashing a chosen suffix from the published digest.
  4. Forged message m ‖ padding ‖ &admin=true with a valid forged tag.
The attack does NOT needIt actually exploits
Recovering K · finding a collision · inverting the hash · breaking the compression functionThe visible digest as a continuation state · the known original message · a correct key-length guess · the unsafe design H(K‖m)

Length extension is a construction failure: secure primitive + unsafe composition = insecure system T3.

HMAC: the standard fix

HMAC(K, m) = H( (K′ ⊕ opad) ‖ H( (K′ ⊕ ipad) ‖ m ) )

The visible tag is the outer hash, not the state after hashing K ‖ m, so the length-extension strategy no longer applies. Use the library: hmac.new(key, msg, hashlib.sha256), and verify with hmac.compare_digest (constant time), never ==. Do not design your own MAC.

3.3Public-key crypto and RSA

HMAC assumes a shared secret already exists. Public-key crypto adds a key pair: the public key is distributed widely (verify / encrypt roles) and the private key stays secret (sign / decrypt roles). Public does not mean trusted: binding the key to an identity is a separate problem (§3.5).

RSA: n = p·q public (n, e) private d c = mᵉ mod n m = c^d mod n

The trapdoor is tied to factoring n: with p and q you can build d; given only a large n, factoring is assumed infeasible for classical attackers. Textbook RSA is deterministic and structurally unsafe. Encryption needs randomized padding (OAEP); signatures need proper encoding (RSA-PSS). The primitive is not the protocol T3.

3.4Diffie–Hellman and the man-in-the-middle

Alice: secret a, sends A = gᵃ mod p Bob: secret b, sends B = gᵇ mod p shared: Bᵃ ≡ Aᵇ ≡ gᵃᵇ mod p

A passive observer sees p, g, A, B and should not be able to recover a, b or gᵃᵇ (discrete-log-style hardness, with properly chosen parameters; the lab’s p = 23, g = 5 are toys). DH is key agreement, not authentication. Neither side gets proof of who sent the value it received.

Eve did not solve the discrete logarithm. Encryption did not fail. The missing property is authentication of the DH exchange T4. Alice and Bob both “succeed” and are still insecure.

Fix: bind the exchange to identities. The server’s certificate proves its public key; the server signs the key-exchange transcript; the client verifies identity + DH values. The certificate does not “encrypt the session”; it authenticates who owns the key that signed the exchange. TLS 1.3 does exactly this in §6.6; OpenSSH does it with host keys (lab Part C below).

3.5Signatures, certificates and choosing the right primitive

Digital signature: σ = Sign(SK_A, m), checked with Verify(PK_A, m, σ). Anyone with the public key can verify; only the private-key holder can sign.

PrimitiveSecretIntegrityOrigin authenticationPublicly / third-party verifiable
HashNoneAccidental change / fingerprint onlyNoAnyone can recompute (so it proves nothing about origin)
MAC / HMACShared keyYesOnly within the key-sharing groupNo: Bob could have made the tag himself, so no non-repudiation

Whose public key is it? If Eve hands Bob “Alice’s public key”, possession of a key is not identity, and MITM remains possible. A certificate is a signed statement binding subject (e.g. example.com) + public key + metadata (validity, issuer), made useful by the issuer’s signature.

Chain of trust: Trusted Root CA → Intermediate CA → Server certificate. The client trusts root public keys in its trust store; each CA signs the certificate below it. (TLS’s Certificate message: §6.5. DNSSEC builds the same idea along the DNS tree: §5.7.)

3.6Forward secrecy

The recorded-traffic problem: an attacker records ciphertext today and steals the server’s long-term key years later. Without forward secrecy, old sessions may be decrypted. With it, old session keys stay unavailable.

Mechanism: ephemeral DH. Fresh DH exponents per session derive the session key and are erased after use. The long-term signing key only authenticates the DH transcript, so stealing it later does not reveal old ephemeral secrets.

Modern protocols compose: certificates for long-term identity, ephemeral DH for session secrets, signatures/MACs to bind the handshake transcript, AEAD for application data. The security comes from the composition.

3.7Randomness

Keys (unpredictable), nonces (often unique), IVs (unique or unpredictable), DH exponents (secret, unpredictable), signature nonces (must not repeat or be predictable), session tokens (unguessable) all depend on it T5.

General PRNGCSPRNG
For simulation/statistics; may be predictable from its state. Example: Python random.Computationally unpredictable, backed by OS entropy. Use secrets.token_bytes(32) or a crypto library for keys and tokens.
  • Debian OpenSSL: a packaging change reduced key-generation entropy; keys came from a small, enumerable space. Strong math, catastrophically weak keys. The implementation environment is part of the security system.
  • Nonce reuse: repeating a nonce under the same key in CTR/GCM-style modes repeats keystream or breaks authentication; repeated or predictable signature nonces can also break signature schemes.

Week 4 · lecture

4 · HTTP & sessions

Core question: after the user logs in once, what authenticates the next HTTP request? Main claim: if a network attacker can read a bearer session token, they may not need the password any more.

4.1HTTP on the wire

For security, treat HTTP as structured text-like bytes over a TCP connection, which a browser, curl, a Python socket or a proxy can all produce.

POST /login HTTP/1.1                         ← request line: METHOD SP TARGET SP VERSION
Host: localhost                              ← headers (CRLF line endings)
Content-Type: application/x-www-form-urlencoded
Content-Length: 29                           ← how many body bytes to read
                                             ← empty line: end of headers
username=alice&password=week4                ← body

HTTP/1.1 200 OK                              ← status line
Set-Cookie: session=abc123                   ← server sets state
Content-Length: 13

Hello, Alice!
  • Security-relevant headers: Host, Cookie, Authorization, Content-Type, Content-Length. The key one this week is Cookie: session=….
  • Status families: 2xx success, 3xx redirect, 4xx client problem, 5xx server problem (200, 302, 401, 403, 404). A status code is not security: the application’s authorization logic decides which one to return.
  • GET usually asks for a resource (but still carries sensitive headers like Cookie). POST usually submits a body.

“POST hides data” is false. Over plaintext HTTP a passive observer reads the POST body like any other bytes. Transport protection is what matters.

4.2Statelessness and sessions

HTTP requests are conceptually independent; even on a persistent TCP connection the protocol does not remember who you are. After POST /login, how does GET /profile prove it is still Alice? The application adds a session:

  1. Client → server: username / password.
  2. Server verifies, generates a random token S, stores sessions[S] = {user: "alice", role: "user", …}.
  3. Server → client: Set-Cookie: session=S.
  4. Later requests: Cookie: session=S; server looks up S → Alice.

The token is small; the authority attached to it can be large. Server-side session: cookie holds a random ID, server holds the record. Client-side token: the token carries claims itself (e.g. signed tokens) and still needs confidentiality and verification rules.

4.3Bearer tokens and session hijacking

Bearer model: whoever bears the token can use it. Possession is enough T7.

Examples beyond cookies: API keys, OAuth access tokens, password-reset links, temporary download links, magic-login URLs. The password establishes identity once; the session cookie authenticates every later request until expiry or logout, so it becomes the practical target.

Session hijacking: Eve observes Cookie: session=7a09cdef, sends her own request with the same cookie, and the server maps it to Alice. Eve never needed the password.

Properties cascade T2: exposing the cookie violates confidentiality; reusing it violates session authentication; modifying traffic violates integrity; a DoS violates availability. The password can stay secret while the session is hijacked.

4.5Session lifecycle

  • Generate with a CSPRNG (§3.7): long, unguessable, bound to server-side validity state T5.
  • Rotate after login and privilege changes. Otherwise session fixation: the attacker plants a known session ID before authentication and it becomes authenticated. Do not let the attacker choose the token that later becomes authenticated.
  • Invalidate server-side on logout. Deleting the cookie on the client is not enough if the server still accepts it.
  • Limit lifetime and scope. Short lifetimes reduce exposure but cost usability. (Design question: what happens to all active sessions after a password change?)
  • Transmit authenticated sessions only over HTTPS; set Secure and HttpOnly; avoid mixed HTTP/HTTPS session behaviour; consider HSTS against downgrade or accidental HTTP; keep authorization separate from authentication.

A cookie is protected in transit only if the browser never sends it over an exposed channel. Session security is a system, not a single header.

4.6What HTTPS fixes and what it does not

HTTPS = HTTP carried over TLS (HTTP → TLS → TCP → IP). Cookies are inside HTTP, so TLS protects them in transit.

Confidentiality of headers and body · integrity in transit · server authentication through certificate validation · protection against simple on-path cookie theftXSS · SQL injection · broken authorization · malicious browser extensions · endpoint malware · server compromise · weak session lifecycle design

Assumptions: certificates are validated, endpoints are not compromised, and the application uses HTTPS consistently. If the client skips certificate validation, an active attacker can impersonate the server: HTTPS relies on authenticated TLS, not just encryption T4.

Scope boundary. HTTP transports requests; the application decides whether each one is allowed (a valid cookie means “this request belongs to session S”, not “every action is permitted”). XSS = attacker script running in the victim’s browser context; it shows session theft is not only sniffing. SQL injection = unsafe query construction from input (HTTP input → app → database); not a network interception problem.

5 · DNS

Applications use names; packets need addresses. If the DNS answer changes, the device connects to a different machine and the application code never notices. Web, email (MX), APIs, CDNs, certificate issuance checks and monitoring all depend on it. DNS was designed in the 1980s without security.

5.1The tree, the actors and a lookup

  • Namespace tree: root . → TLD (com, tr) → domain/zone (example.com) → host (www.example.com). Responsibility is split by delegation: no single server knows every answer. Trust is split too: root → TLD → operator; a false link redirects everything below it.
  • Zone: the part of the tree one operator manages, served by its authoritative servers.
  • Stub resolver: minimal client in your OS; forwards questions. Recursive resolver (ISP, campus, 1.1.1.1): does the full search and caches. Shared by many users, so it is the high-value target.
  • Root / TLD servers mostly give referrals (“ask these servers next”).

Recursive vs iterative: the client sends a recursive query (“get me the final answer”, flag RD; server advertises RA). The resolver resolves iteratively, following referrals hop by hop. Both happen in one lookup, at different hops; “DNS is recursive” alone is incomplete.

5.2Records, caching and TTL

A resource record = NAME TYPE CLASS TTL RDATA, e.g. www 300 IN A 192.0.2.20. The security question for every record: who is authorised to assert this? Classic DNS has no cryptographic way to check.

Glue records: addresses of name servers supplied in the additional section of a referral (needed when ns1.example.com lives inside the zone it serves). Operators run at least two name servers.

TTL = seconds a cache may keep a record. Short TTL: fresher, more lookups. Long TTL: faster, but stale or poisoned data lingers, and a forger picks the TTL of the forged record. Caching also cuts both ways for attackers: a cached name produces no outbound query, so there is nothing to forge until it expires.

5.3Wire format

Binary protocol. Queries and responses share one layout: a fixed 12-byte header, then question, answer, authority, additional sections. The reply copies the ID and question; that copy is the only thing classic DNS uses to match replies.

Parsers must validate RDLENGTH against the real message size and handle compression pointers safely; bugs here caused real vulnerabilities.

Transport: mostly UDP port 53; TCP 53 for large (TC-flagged) responses and zone transfers. UDP has no handshake, so a reply is matched only by its contents and addressing, which makes spoofing and racing possible.

Cache poisoning: plant a false record in a shared resolver’s cache once; every client of that resolver receives it until the TTL expires. No client is hacked. It is a protocol-level weakness: classic DNS cannot verify that a reply is authentic.

A resolver accepts a UDP reply if: it arrives at the query’s source port · claims the queried server’s address (port 53) · has the same TXID · repeats the exact question · arrives while the query is outstanding (first match wins; the real reply arriving later is discarded). An off-path attacker knows the server and (often) the question; the unknowns are TXID and source port, and the timing is a race.

5.5The Kaminsky attack (2008) and bailiwick

Problem it solved for attackers: once a name is cached (or a race is lost and the real answer is cached), there is no new query to forge until the TTL expires: only a few attempts per day.

  1. Trigger a lookup of a random, never-cached subdomain (a8f1.victim.com, q91z.victim.com, …): guaranteed cache miss, fresh outbound query, new race. The attacker also knows the exact QNAME.
  2. Flood forged replies guessing the TXID (and port).
  3. The real payload sits in the authority/additional section: victim.com. NS ns.attacker.example. (delegation data).
  4. Lose? Pick a new random name immediately. Win? The resolver now sends every victim.com query (www, mail, login…) to the attacker.

Against 2008 resolvers with a fixed source port, only 16 bits stood in the way, so success came in minutes. Response: emergency source-port randomisation, stricter bailiwick rules, renewed push for DNSSEC (root signed in 2010).

Bailiwick: a server’s area of responsibility. Rule: do not cache unrelated, unsolicited authority. Ask example.com’s server about www.example.com and it slips in bank.com A 203.0.113.66: discard. Limitation: Kaminsky’s forged NS records for victim.com are in-bailiwick, so bailiwick alone does not stop it. Resolvers also rank trust so “extra” data does not overwrite authoritative data.

Defence families

Make forgery hard to get right (probabilistic)Make forgery detectable (cryptographic)

DNS poisoning is a data-origin authentication problem expressed as a network race. The resolver had no memory-corruption bug; randomness was quietly being used as authentication.

5.6DNS tunneling

Not lying in answers, but using DNS as a covert channel. Data is encoded (Base64/Base32) into subdomain labels, e.g. SGVsbG8.attacker.example (“Hello”); replies carry data back, often in TXT records. Path: compromised host → the organisation’s own recursive resolver → attacker’s authoritative server. The malware never contacts the attacker’s IP directly, so IP blocklists miss it. Uses: malware command-and-control, data exfiltration, bypassing captive portals.

Why hard to block: networks need DNS; tunnel queries are valid DNS; DNS is often logged less than web traffic; legitimate services (CDNs, antivirus, telemetry) also produce odd names. Better: force clients to the internal resolver (block outbound 53 elsewhere), log centrally, filter known-bad/new domains.

Detection signals: long or high-entropy labels near the 63-char limit · unusual query volume or regular beaconing from one host · many unique subdomains under one rare or newly registered domain (each is a cache miss that reaches the attacker, which is what a tunnel needs) · many TXT/NULL queries · large responses, odd timing. These are evidence, not proof: compare against a baseline and correlate to limit false positives.

Tension: clients using DoH to an outside resolver hide DNS from the organisation, which helps privacy and also helps tunnels hide (§5.8).

Authenticated denial

You cannot pre-sign “does not exist” for infinitely many names, and one generic signed NXDOMAIN could be replayed to make real names vanish (a DoS). That is an information-disclosure (confidentiality of zone contents) issue, not an integrity failure. NSEC3 uses hashed names (SHA-1, optional salt/iterations), so walkers collect hashes; predictable names can still be cracked by an offline dictionary attack. NSEC3 is not encrypted DNS.

5.8DoT, DoH and which defence stops which attacker

  • DoT (DNS over TLS, TCP 853): DNS inside TLS between client and resolver. Confidentiality + integrity on that link, and authenticates the resolver via its certificate. Dedicated port: easy to identify or block. (Android “Private DNS”.)
  • DoH (DNS over HTTPS, 443): DNS message inside HTTP inside TLS. Same protection, but blends with web traffic: harder to censor, and can bypass corporate monitoring and filtering. Browsers can do it independently of OS settings.
  • Both: the resolver still sees every query, and its upstream queries are usually plain DNS. They do not prove answers are genuine T6.

6 · TLS 1.3 up to the 1.2 vs 1.3 comparison

TLS is the first protocol in the course where almost every earlier idea appears together: the network adversary (§1), AEAD (§2), DH, signatures, certificates and forward secrecy (§3), the cookie-stealing proxy (§4), and “authenticity vs privacy” (§5). Core idea: a secure channel needs authentication + fresh key establishment + integrity-protected records + correct trust decisions. Lose one and the channel can be attacked even with perfect encryption.

6.1Why TLS exists and where it sits

The Week 4 proxy read credentials and bearer cookies and rewrote responses without breaking any cryptography, because there was none. That is the adversary TLS is built for: a network attacker who can observe, inject, delete, replay or modify traffic (Dolev–Yao style, §1.3).

Plain HTTPHTTP over TLSProperty

  • HTTPS is HTTP semantics carried through TLS (port 443); the “S” is not a different application protocol. TLS also protects IMAPS, SMTPS, LDAPS, DoT, MQTT, database connections.
  • Stack: Application → TLS (handshake + records) → TCP → IP → Link. TCP gives a reliable byte stream with no confidentiality or peer authentication. DTLS and QUIC carry TLS ideas over UDP.
  • TLS is a state machine: an endpoint must know which messages are legal next, which secrets exist, which keys are active, and whether authentication and transcript checks are complete. Phases: plaintext Hellos → handshake keys → application keys. Unexpected transitions have caused real attacks (2015 state-machine bugs where clients skipped authentication if the attacker omitted messages). Reject anything unexpected.
  • Lifecycle: Negotiate (version, algorithms, key share) → Derive (handshake secrets) → Authenticate (certificate + transcript) → Confirm (Finished) → Protect (application records). Abort if any step fails.

TLS gives confidentiality of content, not anonymity.

6.3Record layer

TCP has no message boundaries and no protection, so TLS creates its own framing: records, each at most 2¹⁴ = 16,384 bytes of plaintext. Pipeline: plaintext → fragment → protect (AEAD + nonce + AAD) → transmit over TCP → verify the tag before use.

  • Record structure: header (TLS 1.3: 5 bytes: outer type shown as application_data, legacy version 0x0303, 2-byte length) · ciphertext (includes the real inner content type, so observers cannot tell handshake from application records) · tag (16 bytes for AES-GCM). Example: 1,000 bytes of HTTP → 5 + 1,000 + 1 + 16 = 1,022 bytes on the wire.
  • AEAD (from §2.5) is required in TLS 1.3:
(C, T) = AEAD_Encrypt(K, N, P, A) AEAD_Decrypt(K, N, C, A, T) → P or FAIL

K = traffic key from the handshake · N = per-record nonce · P = plaintext · A = associated data: authenticated but not encrypted (the TLS 1.3 record header) · C = ciphertext · T = tag. Change one bit of A and decryption fails even though A was never encrypted. AEAD cleanly separates “must be secret” from “must be authentic”. There is no partial or unauthenticated output: unauthenticated plaintext must never reach the application.

Nonces and sequence numbers

nonce = static IV (from the handshake) ⊕ 64-bit record sequence number (left-padded)

6.4The TLS 1.3 handshake at a glance

The handshake must: agree a version · agree algorithms (AEAD + hash, key-exchange group, signature algorithm) · establish shared secret material (ephemeral (EC)DHE, optionally a PSK for resumption) · authenticate the server (X.509 chain + CertificateVerify) · bind everything into a transcript · derive separate handshake and application traffic secrets.

Key epochs

One connection ≠ one key. Initial (Hellos, plaintext) → Handshake (encrypted certificate, CertificateVerify, Finished) → Application (data) → Updated (optional KeyUpdate for fresh keys, e.g. for AEAD usage limits or to limit damage if a key leaks). Each direction has its own keys per epoch, and epochs are derived separately (key separation).

Transcript hash

Transcript-Hash(M₁ … Mₙ) = Hash(M₁ ‖ M₂ ‖ … ‖ Mₙ) (the suite’s hash, e.g. SHA-256)

Signed by CertificateVerify, MACed by Finished, and mixed into key derivation. Change anything (version list, key share, certificate, an ALPN value) and signatures fail, Finished fails and the derived keys differ. Like both parties signing a fingerprint of every page of a contract.

Certificate = “this key belongs to bank.example”. CertificateVerify = “and I hold that key, right now, in this handshake”. Finished = “we derived the same keys and saw the same messages”.

6.6Raw DH vs authenticated TLS key exchange

This closes the story from §3.4 T4. Raw DH: Mallory replaces both public values and holds two secrets. TLS 1.3:

  1. The Certificate binds the server’s long-term public key to its hostname (validated via PKI).
  2. CertificateVerify signs the transcript hash, which includes both key shares. If Mallory replaced the client’s share, the signed transcript does not match what the client sent. She cannot sign as the real server (no private key) and cannot get a CA certificate for that hostname.
  3. Finished confirms both sides derived the same secret from the same transcript.

The mathematics of DH was not broken in Week 3. The missing property was authentication.

Same lesson elsewhere: OpenSSH host keys + known_hosts (Lab 3C), HTTPS certificate validation (§4.6), and TLS’s certificate check catching DNS lies, since a forged DNS answer leads to a server without the right certificate (§5.4).

6.7Client authentication and mTLS

  • Web default: TLS authenticates the server; the user then authenticates inside the channel (password, passkey, cookie).
  • TLS 1.3 can authenticate the client: server sends CertificateRequest (encrypted, after EncryptedExtensions); client replies with Certificate, CertificateVerify and Finished. Post-handshake client authentication is also possible.
  • mTLS (mutual TLS): both sides present certificates. Common in service meshes (short-lived certs per microservice, “zero trust”), enterprise VPN / Wi-Fi (EAP-TLS) and IoT devices.
  • It authenticates a cryptographic identity; authorization is still separate (a compromised service with a valid certificate is still “authenticated”). Operational cost: every client needs keys, certificates, renewal and revocation.

Symmetric crypto · Week 2

An ECB-encrypted image still shows the picture. Which property failed, and is AES broken?
Confidentiality (structure/equality leaks). AES is fine; the mode is the failure: ECB is deterministic, so equal plaintext blocks give equal ciphertext blocks. Not IND-CPA secure. §2.5
A CTR nonce was reused under the same key. What does the attacker learn, and what if one plaintext is known?
C₁ ⊕ C₂ = M₁ ⊕ M₂ (the keystream cancels). With M₁ known: M₂ = C₁ ⊕ C₂ ⊕ M₁. §2.5
A modified CBC ciphertext is accepted. Which property is missing?
Integrity/authentication. CBC is malleable: flipping bits in Cᵢ₋₁ flips the same bits in Pᵢ. Encryption alone ≠ integrity; use AEAD. §2.5
AEAD tag verification fails. Should the decrypted plaintext be used?
Never. Verify before use; AEAD decryption returns either plaintext or FAIL. §2.5 §6.3
Which parameters must be secret, and which must only be unique or unpredictable?
Key: secret. IV (CBC): public but unpredictable. Nonce (CTR/GCM): public but unique per key. Public does not mean arbitrary. §2.5

Integrity & public key · Week 3

Did the length-extension attacker recover the key or break SHA? Why does HMAC resist?
Neither. It abused H(K‖m): the visible digest is the Merkle–Damgård state after K‖m, so hashing continues from it after a key-length guess and glue padding. HMAC’s visible tag is the outer hash of an inner hash, not that state. §3.2
In the DH MITM, did Eve solve discrete log? Which property was missing, and what fixes it?
No; she ran two honest DH exchanges with her own values. Missing: authentication of the exchange. Fix: certificates + a signature over the key-exchange transcript (TLS CertificateVerify), or host keys in SSH. §3.4 §6.6
How does ephemeral DH give forward secrecy?
Session keys come from fresh per-session DH secrets that are erased afterwards. The long-term key only signs/authenticates, so stealing it later cannot recompute old session keys from recorded traffic. §3.6
What does OpenSSH store in known_hosts, and what happens if users disable host-key checking?
The server’s host key (fingerprint) from the first trusted connection. Later connections compare against it and warn on change. Disabling checks (StrictHostKeyChecking=no) brings back the raw-DH MITM. Lab 3C
Why must session tokens and keys come from a CSPRNG? Give a real failure.
General PRNGs can be predicted from their state; a CSPRNG is unpredictable and backed by OS entropy. Debian OpenSSL’s entropy bug made keys enumerable. §3.7

HTTP & sessions · Week 4

Why is a session cookie often equivalent to a credential? How can a confidentiality failure become an authentication failure?
It is a bearer token: possession is enough for the server to treat the request as that session. Reading it (confidentiality) lets the attacker replay it and be accepted as the user (session authentication), without the password. §4.3
Why does POST not protect login data?
POST only puts data in the body. Over plaintext HTTP the body is as readable as headers. Only transport protection (TLS) hides it. §4.1
What does Secure protect against? What does HttpOnly not protect against?
Secure: the cookie being sent over plaintext HTTP. HttpOnly does not stop the browser sending the cookie, does not stop injected script from acting as the user, and does not fix authorization bugs. §4.4
Explain how an on-path attacker moves from passive observation to active replay.
Read → replay → tamper. Passively read Cookie: session=S (confidentiality), then send a new request carrying S (active; authentication), and as an interception proxy also rewrite requests/responses (integrity). §4.3

DNS · Week 5

With 20,000 forged replies in one race, compare success with TXID only vs TXID + random port.
TXID only: 20,000/65,536 ≈ 0.31. TXID + port: 20,000/2³² ≈ 4.7 × 10⁻⁶ (≈ 1 in 215,000). Still a probability argument, not authentication. §5.4
What made Kaminsky practical, and why is poisoning NS worse than poisoning one A record?
Random never-cached subdomains force a new upstream query each time, giving unlimited races. The payload is forged NS delegation data, which sends every future query for the whole zone to the attacker. §5.5
What does bailiwick checking prevent, and why doesn’t it stop Kaminsky alone?
Caching unrelated, unsolicited records for zones the responder is not responsible for. Kaminsky’s forged NS records for victim.com are in-bailiwick for a reply claiming to be from victim.com’s server. §5.5
Name DNSKEY, RRSIG and DS in one line each.
DNSKEY: zone’s public key. RRSIG: signature over one RRset, valid for a date range. DS: parent-held, parent-signed hash of the child’s key-signing key. §5.7
Why can’t a zone just sign “NXDOMAIN”, and which security property does zone walking affect?
Infinitely many names, and one generic signed NXDOMAIN could be replayed against real names. NSEC/NSEC3 sign the gaps. Zone walking (NSEC) affects confidentiality of zone contents, not integrity. §5.7
Does DoH stop a malicious resolver from lying? Does DNSSEC hide your queries?
No and no. DoH only encrypts the pipe, which ends at the liar; DNSSEC validated on your own device detects lies for signed zones. DNSSEC signs data but encrypts nothing. §5.8
Encode “a.io” in DNS wire format.
01 61 02 69 6f 00 (6 bytes). §5.3

TLS 1.3 · Week 6 (slides 1–52)

The certificate is valid. Why is CertificateVerify still needed?
Certificates are public; anyone can replay one. CertificateVerify proves possession of the private key, bound to this handshake’s transcript (including both key shares). §6.5
What exactly does a TLS 1.3 cipher suite name specify? Compare with TLS 1.2.
Only AEAD + hash (e.g. TLS_AES_128_GCM_SHA256). Key exchange and signature algorithm are negotiated by extensions. TLS 1.2 names bundled key exchange, authentication, cipher and PRF hash. §6.5

Foundations · Week 1

Is an on-path attacker always active? Give a counter-example.
No. Position and behaviour are separate dimensions. The Week 1 lab sniffer is passive on-path: it only observes. §1.3
Alice and Bob share an HMAC key. Can Bob prove to a judge that Alice sent a message?
No. Bob holds the same key and could have produced the tag himself, so a MAC gives no third-party evidence (no non-repudiation). A digital signature can, assuming the key binding is trusted. §3.5
What does Dolev–Yao assume about cryptography, and what is it good for?
Cryptography is ideal (no decryption without the key) while the network is fully hostile (read, block, delay, reorder, replay, inject, modify, impersonate). It finds protocol logic flaws such as replay and missing authentication. The computational model instead asks whether an efficient (PPT) attacker gains non-negligible advantage. §1.3
Is STRIDE a proof that a design is secure?
No. It is a threat-generation checklist and shared vocabulary. It does not prove security, is not a complete attacker model, and does not guarantee all threats were found. §1.2

Symmetric crypto · Week 2

List the four requirements for OTP perfect secrecy and why it isn’t used for Internet traffic.
Truly random key, at least as long as the message, secret, never reused. Key distribution: a 10 GB file needs 10 GB of pre-shared key. §2.2

Integrity & public key · Week 3

What is the generic collision cost for a 256-bit hash, and why?
About 2¹²⁸, by the birthday bound: q samples give ~q²/2 pairs, so collisions appear around q ≈ 2ⁿᐟ². §3.1

HTTP & sessions · Week 4

What is session fixation and its fix?
The attacker makes the victim use a session ID the attacker knows before login; after login it becomes authenticated. Fix: issue a fresh token after login and privilege changes. §4.5

TLS 1.3 · Week 6 (slides 1–52)

Why does TLS need its own record layer above TCP?
TCP is a byte stream with no message boundaries, no encryption and no authentication. Records (≤ 16 KB) are the units of protection and carry the per-record sequence state. §6.3
The TLS 1.3 record sequence number is never sent. How does it still stop reordering and replay inside a connection?
It is mixed into the nonce (IV ⊕ seq). A record moved to another position is decrypted with the wrong nonce and fails the AEAD tag check. §6.3
Why did TLS 1.3 remove CBC suites?
CBC + HMAC as MAC-then-encrypt required padding checks before MAC checks, creating distinguishable errors/timing (padding oracles: Lucky13, POODLE). AEAD-only gives one interface and one failure mode. §6.3
Which TLS 1.3 handshake messages are plaintext, and why can’t they be encrypted?
ClientHello and ServerHello. No shared secret exists until both key shares are exchanged; everything after ServerHello uses handshake keys. §6.5
An attacker deletes the strongest cipher suite from ClientHello. What catches it?
The transcript hash changes, so CertificateVerify and Finished (HMAC over the transcript) fail, and the derived keys differ. Negotiation integrity. §6.5
Is the visited hostname hidden by TLS 1.3?
Not by default: SNI is in the plaintext ClientHello. ECH encrypts it. IP addresses, timing and sizes remain visible regardless. §6.5 §6.2
Does mTLS decide what a client may do?
No. It authenticates a cryptographic identity; authorization remains a separate application decision. §6.7
